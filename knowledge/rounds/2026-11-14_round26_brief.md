## PART B — THE WORK (one issue, four requirements)

### W1 — The composer must be EMPTY after a verified send, in every send path

- **R1.1** Clearing must work on Gemini's real composer: clear the text through the **DOM**
  (the contenteditable that holds it, including any inner editor element), then dispatch the
  `input` / `change` events that a rich-text editor listens for, so the editor's own state
  is emptied and not just the visible text. Keep the keyboard route (`Control+A` +
  `Delete`) as a FALLBACK, but do not rely on it alone.
- **R1.2** The clear must run in **every** send path - the companion extension's
  `click_send` path AND the pure-Python path - and it must run whenever the send was
  verified, even when the snippet-count proof (`snippet_count_after > snippet_count_before`)
  is unavailable. A prompt that stays in the composer is a DUPLICATE-SEND hazard, not a
  cosmetic issue.
- **R1.3** It must NEVER remove text that is not our prompt. Compare the composer text
  against the prompt (the probe snippet) and leave foreign text alone - a human may have
  typed something.
- **R1.4** It must **ALWAYS log its outcome**: `composer cleared (N chars removed)` or
  `composer left as is: <reason>`. A silent failure is a bug (F5).
- **R1.5** When a verified send leaves our prompt in the composer, the lane must say so in
  the pre-flight summary (e.g. `composer after send : NOT EMPTY (N chars)`), so the log
  never claims a clean send while the prompt is still armed.

### W2 — A queued steering turn must count as "already sent"

- **R2.1** A `user-query` whose parent carries the class `queued-steering-turn` is a message
  that was submitted while Gemini was already working. If it carries OUR prompt, the prompt
  is already in that conversation: the bridge must NOT paste and send it again.

  (`a queued steering turn with this prompt already exists`) and go to the delivery phase.
- **R2.3** The duplicate-prompt check must keep stripping the upload chip and the
