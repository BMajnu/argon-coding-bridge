### WORK UNIT 1 — Make the base64 cap real, and route big archives zero-copy

**Problem:** F1 + F2 + F3. The cap exists but is never read, so an archive up to 64 MB is
base64-encoded into the page; the zero-copy CDP route that already exists is never used for
the archive.

**Requirements**

- **R1.1** `MAX_BASE64_ATTACH_BYTES` must be READ by `dispatch_argon.py` and must be the
  **single source of truth**. Delete the competing idea of a second constant
  (`MAX_DATATRANSFER_BASE64_ARCHIVE_BYTES`) — the patch script
  `skills/argon-coding-bridge/scripts/patches/patch_bridge_large_archive.py` currently
  proposes it; make that script verify the REAL cap instead of proposing a new one.
- **R1.2** `_attach_zip_via_datatransfer()` must **not** base64-encode an archive larger than
  the cap. It must return the distinct reason `"size_cap_exceeded"` and the caller must fall
  through to a zero-copy route. It must never base64 the file just to discover it is too big —
  read `zp.stat().st_size` FIRST, before `read_bytes()`.
- **R1.3** The archive attach route order must be:
  1. CDP `DOM.setFileInputFiles` (the existing `_attach_zip_via_cdp_dom_file_input()`) — zero copy;
  2. Playwright `set_input_files` (the existing routes at 7120-7155) — zero copy;
  3. the companion-extension `attach_archive` (base64) — **only** for archives at or below the cap;
  4. the OS file dialog — only when explicitly allowed (`ARGON_ALLOW_OS_FILE_DIALOG`).
  Archives **at or below** the cap keep today's behaviour exactly (F4: 39.22 MB works today —
  do not change it).
- **R1.4** The base64 route must be skipped, not failed: when the cap is exceeded the bridge
  must still attach the archive through a zero-copy route. If no zero-copy route is available
  it must log a loud warning and continue with the base64 route — **the attach must never fail
  because of the cap**.
- **R1.5** The bridge must print, in ONE line, before the attach:
  `archive <name>: <bytes> bytes | cap <MAX_BASE64_ATTACH_BYTES> | route <chosen> | base64 <yes|no>`.
- **R1.6** The cap must be overridable from the environment the way it already is
  (`ARGON_MAX_BASE64_ATTACH_MB`), and the effective value must be printed.

### WORK UNIT 2 — The account slot must be unambiguous

**Problem:** F7 + F8 + F9 + F10. `--slot /u/9/` silently means *pool slot 9*, which is browser
account `/u/8/`. A brief that labels a lane "/u/9/" sends the prompt to the wrong account.

**Requirements**

- **R2.1** Add a **new, additive** CLI flag `--account-index N` that addresses the browser
  account directly (N = the 0-based position in the browser's `account_info` list). It resolves
  N → the pool slot that owns it and **refuses** when N is not a registered browser account.
  Existing flags keep their exact current meaning (`--slot` stays a POOL slot).
- **R2.2** The dispatch must print, BEFORE the send, one unambiguous line in this shape:
  `slot /u/9/ (majnu.charitabari@gmail.com) = browser account index /u/8/ -> https://gemini.google.com/u/8/app`
  and it must **WARN** when the resolved index differs from the slot number, because that is
  the case that silently sends to another account.
- **R2.3** The brief summary file (`--brief-summary`, produced by `prepare_brief.py`) and the
  manual hand-off pack (`--manual-handoff`) must carry the **resolved browser URL**, never a
  pool-slot number. A human must be able to read one line and know which Google account
  receives the prompt.
- **R2.4** The resolved URL must also be written into the run log next to the existing print
  at `dispatch_argon.py:11342-11345` (reuse that line, do not add a second competing one).
- **R2.5** `--account-index` and `--slot` must not be combinable into an ambiguous state: if
  both are given and they disagree, the dispatch must refuse with a named reason.

### WORK UNIT 3 — A large archive needs a fresh chat, and the cap must be real

**Problem:** F5 + F6. A 260.51 MB archive was uploaded although the documented cap is 100 MB, and

**Requirements**

- **R3.3** The bridge must distinguish "the upload is still running" from "the upload failed",

- **R3.4** The bridge must never send the prompt before the upload has finished. If the upload
